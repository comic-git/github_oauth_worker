# Planned CMS Enablement

The intended CMS enablement behavior starts at the worker's `/setup` URL. The creator authorizes their GitHub account and chooses from repositories visible through their GitHub App installations. If the intended repository is absent, the worker links to GitHub to install the App or add repository access; GitHub returns to the existing setup continuation, which verifies the installation before showing its repositories. The creator then chooses a branch, reviews the conversion summary, and explicitly creates a migration pull request. The repository's default branch is preselected, but the creator can choose another branch that GitHub exposes to their authorized App token. Opening the App installation link directly remains supported.

The first authorization remains in a brief, encrypted browser session while the creator visits GitHub to install the App or change its repository access. On return, the worker verifies the untrusted installation ID against GitHub using that token and shows the installation's repositories without another account picker when verification succeeds. A missing, expired, or insufficient discovery token falls back to fresh authorization. The creator can choose **Use another GitHub account** from the setup screens. After repository selection, the worker verifies the user's installation membership and administrator access, binds the selected repository to the short-lived session, and rechecks access and the reviewed migration plan before writing. This usually avoids a second GitHub authorization, but the token may still have GitHub access to other App-installed repositories: the repository binding is enforced by the worker, not by GitHub's token scope. If the discovery token cannot verify access, setup requests a repository-restricted authorization instead. Expired or invalid repository sessions require the creator to start setup again.

The pull request makes the selected branch CMS-ready by retaining its legacy files, adding engine-generated TOML replacements, and configuring the CMS to use the worker. The worker resolves the repository's accepted engine-version selector once to an official engine commit and records that SHA in the pull request for auditability; it does not change the repository's selected engine version. The creator reviews and merges the pull request using normal GitHub controls. After the site deploys, the creator opens the CMS and completes the existing origin-bound login flow.

If the selected branch already has an authoritative `comic_info.toml` with CMS enabled for that repository, branch, and worker, the engine runner checks the main configuration and every page against the same CMS editing rules used by the site build. The worker then reports that setup is complete without creating a PR, even when legacy INI files remain. A TOML-backed branch with CMS disabled, different worker-owned settings, or incompatible pages is not treated as a successful no-op; enabling an existing disabled TOML site remains deferred.

Repeating setup discovers open migration pull requests in GitHub, not from a stored operation record. For the same target revision, the worker compares the current pull request branch with the engine-generated result. Matching files and engine metadata need no write; otherwise the worker adds a Refresh commit on the branch's current head and updates only the engine audit line in the pull request description. Direct edits to the migration branch are not preserved in the final file tree: the selected target branch and the generated migration result determine that tree. A non-force GitHub ref update rejects a competing write. The failure page links back to a fresh review; interrupted branch or description updates can also be retried.

When the target branch advances, its new revision gets a fresh migration branch and pull request so the PR diff remains focused on the migration. After the replacement pull request exists, the worker closes older open migration pull requests against the same target branch and deletes their head branches if no open pull request still uses them. A failed branch deletion is reported on the result page without hiding the ready replacement pull request. The review page links any older pull requests that will be closed. A branch left by an interrupted creation can be reused if no pull request has claimed it; a branch attached to a closed pull request gets a new name.

The review page links an existing migration pull request and labels the action as an update. Its file list compares the proposed migration result with that pull request's current branch, so it shows only files the update will add, change, or remove. An up-to-date pull request has no update action. Confirmation is bound to the exact reviewed migration content and target and engine revisions; if these change before confirmation, the creator must review again. The worker no longer stores migration branch history in Firestore; Firestore remains the source of truth only for OAuth bindings and related enrollment state.

The worker rejects repositories that cannot be migrated safely, including unsupported repository layouts, missing or incompatible engine selectors, partial migrations, unreadable source content, or a user without repository-administrator authority. Errors tell the creator what needs attention without exposing private repository content or credentials.

The default delivery is a pull request because CMS enablement can affect every page metadata file. A future direct-to-default-branch mode may reduce friction for trusted use cases, but it must remain an explicit product choice rather than an implicit side effect of installation.
